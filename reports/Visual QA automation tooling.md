# Let scripts click and Claude judge

The visual QA skill can be built with tools that exist today, but three parts of the concept need to change. First, Google Drive cannot display an HTML file as a webpage. Drive previews HTML as raw source code and stopped hosting pages in 2016. The skill should therefore render the same report to a **PDF**, which Drive previews inline with the screenshots on the page, and store the self-contained HTML next to it as the archive copy. Second, the slow and expensive part is not the browser but Claude deciding every click. The biggest speed and cost lever is to take the model out of the per-step loop: work out each scenario once, save it as a Playwright script, replay that script with no model calls, and use a vision model once per scenario only for what code cannot check. Judging 50 screenshots costs about **two cents on Haiku 5.5**. Third, "Jev AI" is a real product. It is TypeSafe AI's "System One" decision model, which entered early access on **15 September 2026**, and community Claude Code skills hand it each click decision, which it returns in about 100–500 ms. Its authors report runs **1.6–3x faster and 2–5x cheaper**, but only from three-run samples. Jev cannot see screenshots, does not handle iframes, file uploads or shadow DOM, and sometimes reports success when it has failed. It covers the clicking half of the job, so it belongs in the design as an optional plug-in, not the foundation. The hardest problem is a trustworthy pass/fail verdict: in the best published test, roughly three in ten runs that the top screenshot judges called successful had actually failed. The recommended design therefore adds code-based checks and a third verdict, "needs review", alongside pass and fail.

## Every piece exists today, and nobody sells it cheaply as a local skill

Each of the four steps maps to a mature tool. Playwright drives the browser and takes the screenshots, Claude's vision judges them, the Drive API files the results, and a Claude Code skill packages the workflow. The market confirms the demand but does not offer this exact product. AI-native QA tools already turn plain-language scenarios into executed tests, and they fall into three groups. Runtime-agent SaaS includes Momentic and QA.tech, which costs **$499–$1,999/mo** self-serve ([Bugzy comparison](https://www.bugzy.ai/compare/best-ai-qa-tools-2026)). Code-generating tools include TestSprite at $19/mo after free credits ([TestAutomate](https://testautomate.ai/blog/best-agentic-qa-tools/)). Managed human-plus-AI services such as Bug0 start around **$2,500/mo** ([Bug0](https://bug0.com/blog/best-qa-automation-tools-2026)). Most of these prices come from vendor-written comparison pages, and the market is unstable: Octomind turned its product off at the end of May 2026 and wound the company down by June ([Octomind farewell letter](https://octomind.dev/blog/a-letter-to-our-users-customers-and-readers/)). None of these products runs as a local Claude Code skill that drops a screenshot-and-verdict report into the user's own Drive. They keep tests in their own cloud or format and bill per credit or per minute.

The free baseline is Playwright's own Test Agents. They are a planner, a generator and a healer, set up for Claude Code with `npx playwright init-agents --loop=claude` on Playwright 1.56 or later ([Playwright docs](https://playwright.dev/docs/test-agents)). They are expensive to run, though. One developer reported that **the planner alone used 78% of a five-hour Claude Code usage window** ([DEV Community](https://dev.to/ben_weese/building-playwright-agents-lessons-from-the-deep-trenches-3mk7)). The healer has also been seen "fixing" tests by loosening their assertions ([qaskills.sh](https://qaskills.sh/blog/playwright-test-agents-planner-generator-healer-guide)). The closest open-source match to the user's idea is Autodesk's **claude-browser-test-skills** (Apache-2.0). Its source of truth is a plain-language markdown test, and it has four skills: Author, Refiner, Compiler and Runner. The Compiler emits an LLM-free Playwright `.spec.ts`, and the Runner reports pass/fail with screenshots and expected-vs-actual ([GitHub](https://github.com/Autodesk/claude-browser-test-skills)). QA Scout (MIT) adds the report experience the user wants: framed, labelled screenshots of the problem element and a self-contained `report.html` ([GitHub](https://github.com/radyelkasas/qa-scout)). Both projects are very young, with 10 and 0 stars, so the user should copy their designs rather than depend on them. Building is the right call, using Autodesk's author-compile-run pipeline as the template.

The concept as described needs four adjustments:

| As described | What breaks | Tweak |
|---|---|---|
| HTML webpage with embedded screenshots, in Drive | Drive shows `.html` as source text | Render the same HTML to `report.pdf`, which Drive previews inline, and keep `report.html` and `screenshots/` beside it |
| Claude performs the actions on every run | Every step is a slow, metered model turn | Compile each scenario to a Playwright script once, then replay it with zero model calls |
| Pass or fail from looking at the screenshot | Vision judges are biased toward "pass" | Add code-based checks first, split the expected result into key points, and use three verdicts: pass, fail, needs review |
| Free-form scenario list | Ambiguous expectations produce ambiguous verdicts | YAML scenarios with Gherkin-style steps and an explicit, checkable `expected` field |

## Drive shows HTML as source code, so ship a PDF beside it

The one requirement the skill cannot meet as written is a webpage that opens inside Drive. Google stopped serving pages from `googledrive.com/host/` on **31 August 2016** ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2015/08/deprecating-web-hosting-support-in.html)). Since then, Drive's preview has shown uploaded HTML as plain text, and a share link opens Drive's interface around the file, not a rendered page ([NOS Workspace](https://nos-workspace.com/learn/html-file-in-google-drive)). Google's list of file types that Drive can view on the web does not include HTML ([Google Drive Help](https://support.google.com/drive/answer/2423485?hl=en)). A Chromium extension called "Drive HTML Preview" renders self-contained HTML files in a sandboxed frame, but every viewer would have to install it ([GitHub](https://github.com/filipeaaoliveira/google-drive-html-preview)). Embedding screenshots as base64 data URIs also makes the source view worse. Base64 adds about a third to the file size, and a typical 1440×900 PNG screenshot is about 800 KB ([SavePage](https://savepage.pages.dev/blog/png-vs-jpeg-for-screenshots)). Twenty full-size PNGs would therefore produce an HTML file of roughly 20 MB, which Drive's preview shows as a wall of encoded text.

The fix costs almost nothing, because the skill already controls a browser. **Playwright's `page.pdf()` renders the finished HTML into a PDF**, and Drive previews PDFs natively, with images embedded and share links that work. Calling `emulateMedia({media: 'screen'})` first keeps the on-screen styling instead of print styles ([Playwright API](https://playwright.dev/docs/api/class-page#page-pdf)). A landscape or 1280px-wide page and a `page-break-inside: avoid` rule on each scenario card stop a screenshot from being split across two pages. If reviewers need to comment, a Google Doc is the alternative, but it is harder to build. Community reports say Drive's HTML-to-Docs conversion silently drops base64 images ([Latenode](https://community.latenode.com/t/google-docs-api-not-showing-base64-encoded-images-in-html-upload/35170)). The Docs API's `insertInlineImage` requires a **publicly accessible image URL** of at most 2 kB, with images under 50 MB and 25 megapixels ([Docs API reference](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/request#insertinlineimagerequest)). That means briefly exposing screenshots of a staging app to the public internet. The recommended per-run folder is therefore `QA/2026-11-15 Checkout flow/` containing `report.pdf` (what people click), `report.html` (a self-contained copy that renders perfectly once downloaded), `screenshots/`, and `results.json`. Storing screenshots as WebP rather than PNG shrinks them substantially, to about 210 KB against 800 KB for the same 1440×900 capture ([SavePage](https://savepage.pages.dev/blog/png-vs-jpeg-for-screenshots)).

### Upload through a bundled script

The uploader should be a script bundled with the skill, not a model tool call. Screenshots should never pass through Claude's output as base64. A 500 KB PNG becomes about 670 KB of text for the model to emit, which is hundreds of thousands of tokens per image. Google's official Drive MCP server can create folders and files, but it is still labelled a **Developer Preview** and requires a specially flagged OAuth client ([Google Developers](https://developers.google.com/workspace/drive/api/guides/configure-mcp-server)). The Drive connector attached to some Claude clients exposes an undocumented option to upload by local file reference, which avoids the base64 cost. Because it is undocumented, it is not something to build a pipeline on. The robust path for a personal My Drive is a Python script using the Drive API v3 with an OAuth "desktop app" client, a token cached outside the repo, and resumable uploads for files over 5 MB ([Drive API uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads)).

Two traps need avoiding. **Service accounts have no storage quota** in a personal My Drive and fail with 403 `storageQuotaExceeded` ([Fivetran](https://fivetran.com/docs/activations/destinations/available-destinations/google-drive/troubleshooting/service-accounts-storage-quota)), so they only make sense with a Shared Drive. The recommended non-sensitive `drive.file` scope avoids Google's restricted-scope review ([Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)), but it only sees files the app itself created. A hand-made "QA" folder is invisible to it ([rclone docs](https://rclone.org/drive/)). The script should therefore create "QA" itself on first run and cache its folder ID. rclone is a no-code alternative (`rclone copy ./out "gdrive:QA/2026-11-15 Checkout flow"`), but its shared OAuth client ID **stops working during 2026**, so the user would need to create their own ([rclone docs](https://rclone.org/drive/)).

Drive identifies files by ID and allows duplicate names ([rclone docs](https://rclone.org/drive/)). Find-or-create therefore has to search by name, parent and `trashed = false` ([Drive API search](https://developers.google.com/workspace/drive/api/guides/search-files)), create only on a miss, and reuse cached IDs on later runs. Naming run folders with ISO dates (`YYYY-MM-DD topic`) makes them sort chronologically. One risk is unverified: OAuth apps left in "Testing" status have historically issued refresh tokens that expire after seven days. The setup spike below should check this before the user commits to weekly re-authentication.

## Trustworthy pass/fail is harder than clicking

Driving the browser is a solved problem. Deciding whether the result matches "expected: payment form visible with card fields" is not. No public study measures vision models on this exact task (one end-state screenshot against a short expected sentence). The closest independent evidence is a warning. In AgentRewardBench, 12 LLM judges assessed 1,302 expert-labelled web-agent runs, and **no judge exceeded 70% precision**. Claude 3.7 Sonnet scored 68.8% with the accessibility tree and 69.4% with screenshots, which means roughly three in ten runs it called successful had actually failed. Human annotators agreed with each other 89.3% of the time ([AgentRewardBench](https://arxiv.org/html/2504.08942v2)). Rule-based checks had the opposite failure profile: 83.8% precision but only 55.9% recall, because they rejected real successes over small differences in wording ([AgentRewardBench](https://arxiv.org/html/2504.08942v2)). A separate study of 14 LLM validators found true-positive rates above 96% but true-negative rates usually **below 25%**. The judges accepted good outputs and waved through most bad ones ([Beyond Consensus](https://arxiv.org/html/2510.11822v2)). That study covered code feedback, not UI screenshots, but the agreeableness bias points the same way. For a QA tool, the dangerous error is a false pass, and a vision model's "fail" deserves more trust than its "pass".

The judge's design matters more than the model chosen. AgentRewardBench found that judges were misled when they read the executing agent's own claim of success, for example "I applied the filter" when it had not ([AgentRewardBench](https://arxiv.org/html/2504.08942v2)). **The judge must therefore see only evidence**: the screenshot, the URL and a targeted DOM excerpt, never the browsing agent's narration. Splitting the expected result into key points before judging is the core of WebJudge, which reached **83.6–87.0% agreement with humans** ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)). GUISpector, which checks natural-language acceptance criteria against GUIs, reported F1 of about 0.94 on met criteria and 0.87 on unmet ones. Its "partially met" class dropped to 0.631, a sign that partial verdicts are the least reliable ([GUISpector](https://arxiv.org/pdf/2510.04791); figures from secondary summaries). Anthropic's eval guidance says to use "deterministic graders where possible, LLM graders where necessary" and to give the judge a way out by letting it return "Unknown" ([Anthropic engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). One commercial tool shows what to avoid: Momentic's docs say a run "keeps its passed status" if its mobile evaluator returns nothing, which is a fail-open design ([Momentic docs](https://momentic.ai/docs/prompting/writing-assertions)).

Each scenario's verdict should therefore be built in layers:

1. **Gate checks.** These are free: the page loaded without an error status, there were no uncaught console errors, no "Something went wrong" text appeared, and a readiness assertion passed. If a gate fails, the verdict is fail or blocked with no model call.
2. **Code assertions.** Each key point that code can check becomes a Playwright assertion. Use regex or partial matching rather than exact strings, for example `toHaveURL`, a `getByText(/Save\s*20%/)` visibility check, or a partial `toMatchAriaSnapshot` template. These templates are "a constraint, not necessarily a complete serialization" ([Playwright ARIA snapshots](https://playwright.dev/docs/aria-snapshots)).
3. **Vision judge.** Only the visual remainder goes to the vision model: layout, clipping, colour, "looks like yearly pricing". It gets the image first, which Claude's docs recommend ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)), then the key points, and it must write out the evidence before giving a per-point verdict.
4. **Evidence check.** Any text the judge quotes as evidence is checked against `document.body.innerText`. A quote that does not appear on the page downgrades the result to **needs review**.

Any code-assertion failure means fail. Disagreement between layers, or an "uncertain" from the judge, means needs review. The report should show the compiled assertions next to the screenshot, because an LLM-written assertion can pass trivially and humans need to be able to audit the check itself.

Capture discipline handles the failure modes that no prompt can fix. Playwright explicitly discourages waiting for `networkidle` and recommends waiting on assertions ([Playwright Page API](https://playwright.dev/docs/api/class-page)). The skill should wait for the target element to appear and for spinners to clear, then capture a **viewport** shot at `scale: "css"` for the judge, scrolling the target into view if needed. Full-page shots are for the human report only. A 1280×4000 full-page capture gets downscaled to about 824×2576 on Claude's high-resolution tier, which shrinks text to about 64% of its size. Anthropic warns that small or heavily compressed images cause misreads ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). Pixel-diff visual regression (`toHaveScreenshot`) is useful later as an opt-in "lock this approved screen" layer. It detects change, not correctness, and baselines only compare reliably on the environment that produced them ([Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)). All the judge-accuracy numbers above come from 2024–2025 models, so the skill needs its own calibration set rather than borrowed confidence.

## Claude is slow because it reasons at every step, so stop it doing that

The user's sense that Claude-driven browsing is slow and expensive is right about the cause but overstates the dollar amount. Every agent step resends the whole conversation history. A 1280×800 screenshot costs **1,334 visual tokens** on current models ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)), and declaring the API's browser toolset adds about **6,600 input tokens to every request** ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Combining these inputs, a 10-step scenario with one screenshot per step comes to about 145k input tokens. That is about **$0.32 on Sonnet 5.5 uncached, about $0.10 with prompt caching**, and roughly 30–60 seconds of model time. Browser Use measured that each screenshot adds about 0.8 s of inference latency and that output tokens cost about 215 times more time than input tokens ([Browser Use](https://browser-use.com/posts/speed-matters)). Inside a Claude Code subscription, the real cost is wall-clock time and the usage window more than dollars, which is why the 78%-of-a-window planner anecdote matters more than the price per token.

Some widely quoted fixes are outdated. The claim that Playwright MCP burns 114k tokens against 27k for Playwright CLI ([heyuan110](https://www.heyuan110.com/posts/ai/2026-01-28-claude-code-browser-automation/)) has largely stopped being true. A July 2026 re-test of current releases found the two **within about 1% step for step**, because MCP now writes snapshots to disk and returns a file path, as the CLI does ([DEV Community](https://dev.to/aswani25/playwright-cli-vs-playwright-mcp-which-should-you-use-with-claude-code-1olh)). Switching between those tools barely matters. Four levers do:

1. **Act on references, not pixels.** Anthropic's docs note that a scoped accessibility-tree read "often costs fewer input tokens than a screenshot" and that references survive layout shifts ([Anthropic browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)). Vercel's agent-browser adds a reliability bonus: a click fails loudly if the target is hidden or covered by a consent banner ([GitHub](https://github.com/vercel-labs/agent-browser)).
2. **Use a cheaper model for navigation.** Haiku 5.5 costs **$0.10/$0.50 per million tokens** against $2/$10 for Sonnet 5.5, a 20x gap on input ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). On Browser Use's 180-task open-web benchmark, Haiku 5.5 (high) scored 64.3 at 23¢ per task against Sonnet 5.5's 72.7 at $1.53, with similar median times ([Browser Use benchmarks](https://browser-use.com/benchmarks/agents)). Scripted steps on a known app are far easier than open-web tasks, so the accuracy gap should narrow. A request over 100k prompt tokens moves Haiku 5.5 to a tier five times pricier, so trimming old screenshots from history matters.
3. **Run one forked subagent per scenario.** Claude Code skills support `context: fork` and a per-skill `model` ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). Each scenario then gets a small, fresh context instead of inheriting a growing main session, and scenarios can run in parallel. A fresh context per scenario also avoids the stricter per-image limits that apply once a request carries more than 20 images ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)).
4. **Compile once, replay for free.** This is the decisive lever. Playwright CLI can print recorded actions as Playwright code and generate stable locators from refs ([microsoft/playwright-cli](https://github.com/microsoft/playwright-cli)). Stagehand's `cacheDir` replays recorded actions without the LLM ([Stagehand docs](https://docs.stagehand.dev/v3/best-practices/caching)). Skyvern runs cached code and falls back to the agent when it breaks ([Skyvern docs](https://www.skyvern.com/docs/developers/features/code-caching.md)). One write-up cites Skyvern's compiled runs falling from $0.11 to $0.04 and from 279 s to 120 s ([TinyFish](https://current.tinyfish.ai/issue/24/practitioners-corner/article/12828/compile-to-code-the-pattern-that-turns-agent)). A fully compiled Playwright replay goes further: zero model tokens for navigation, seconds per scenario, and parallel workers at no extra cost.

The table below puts the options side by side. The tasks differ across rows, so read it for orders of magnitude, not exact comparisons.

| Approach | Model calls per run | Cost per scenario or task | Time | Evidence quality |
|---|---|---|---|---|
| Claude screenshot loop, Sonnet 5.5, 10 steps | Every step | ≈ $0.10 cached to $0.32 uncached | ≈ 30–60 s | Derived from [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) and [vision docs](https://platform.claude.com/docs/en/build-with-claude/vision) |
| Same loop on Haiku 5.5 | Every step | ≈ $0.016 uncached | Similar | Derived, same sources |
| Browser Use Ultrafast (cloud agent) | Every step, small model | $0.0064 median | 22 s median | Vendor, 12,238 runs ([Browser Use](https://browser-use.com/posts/bu-ultrafast-is-live)) |
| Claude plus Jev (jev-browse) | Jev per step; Claude plans and verifies | $0.44 vs $2.34 for Claude alone | 24.7 s vs 72.8 s | Author, n=3 ([jev-browse](https://github.com/danielnc/jev-browse)) |
| Compiled Playwright replay | None for navigation | $0 in tokens | Seconds | Standard Playwright |
| One vision judgment (add to any row) | 1 | ≈ $0.0004 Haiku 5.5, ≈ $0.009 Sonnet 5.5 | Short | Derived from [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing) |

Judging is the cheap part. One 1280×800 screenshot plus about 1,500 tokens of instructions and 300 tokens of output works out to roughly **$0.02 for 50 scenarios on Haiku 5.5** and $0.43 on Sonnet 5.5. Cloud browsers are cheap too: Browserbase charges $0.10–$0.12 per browser-hour in overage ([Browserbase pricing](https://www.browserbase.com/pricing)). In agent mode, model tokens set the bill. Once scenarios are compiled, the per-step model decisions disappear, and with them most of the spend.

## Jev is real and fast, but it only covers the clicking half

"Jev AI" is not a mishearing. **Jev is TypeSafe AI's first public "System One" model**, named after the fast, intuitive thinking in Kahneman's *Thinking, Fast and Slow*. It entered early access on 15 September 2026 ([TrueFoundry](https://www.truefoundry.com/blog/typesafe-ai-jev); [Overchat](https://overchat.ai/ai-hub/jev-ai)). Jev does not generate text. It receives a page state plus typed questions (pick one option, place on a scale, true/false) and returns calibrated probabilities. TypeSafe prices input at **$0.042 per million tokens with output free**, and advertises "193.6x Faster, 444.6x Cheaper" on workflows shaped for its model ([TypeSafe AI](https://typesafe.ai/)). Coverage puts decision latency at 70–500 ms ([TrueFoundry](https://www.truefoundry.com/blog/typesafe-ai-jev)). About two days after launch, Browser Use released **jev-ultrafast** (MIT, about 24.5k stars), which turns each page into a numbered table of controls and asks Jev for one operation and one target per round trip ([GitHub](https://github.com/browser-use/jev-ultrafast)). Within a week, community Claude Code skills appeared: jev-browse, jev-kit, jev-browser-skill and a QA-focused jev-browser-use. A MindStudio tutorial on pairing Jev with Claude Code describes exactly the pattern the user heard about: Jev picks each click, and Claude plans, types text and verifies ([MindStudio](https://www.mindstudio.ai/blog/how-to-build-jev-browser-agent)).

Every speed number comes from a vendor or a skill author, and every sample is small. jev-browse reports **1.6–3.0x faster and 2.1–5.3x cheaper** runs at the same pass rate, with a median of 24.7 s and $0.44 against 72.8 s and $2.34 for Claude alone, from three runs ([jev-browse](https://github.com/danielnc/jev-browse)). jev-kit measured 314–486 ms per Jev decision against 1.1–1.5 s for Sonnet, and $0.0008 of Claude spend per run against $0.19. On its Wikipedia suite, Jev named 15 of 18 hops in 7.1 s while Sonnet on Playwright MCP named 17 of 18 in 26.0 s. Jev was faster and slightly less accurate, and the author calls the results "directional, not significant" ([jev-kit](https://github.com/jonathanavis96/jev-kit)). jev-ultrafast's own README reports a 25% cut in median task time (9.45 s to 7.09 s) across six runs and warns that the run is "not a general reliability benchmark" ([GitHub](https://github.com/browser-use/jev-ultrafast)). One 60-trial comparison found Jev only **0.81x as fast** as the browser tool built into Codex ([AuroraPixel](https://github.com/AuroraPixel/jev-browser-use)). No independent party has reproduced any of these claims.

Jev's limits fall on exactly the parts a visual QA tool cares about. It is DOM-only, so it cannot look at a screenshot and say whether the layout is broken. jev-ultrafast does not support **shadow roots, iframes, canvas, file uploads, pop-up tabs or nested scrolling** ([GitHub](https://github.com/browser-use/jev-ultrafast)), which rules out embedded payment forms and many component libraries. In MindStudio's test, the agent reported finishing 10 page visits in 77 s, but most of its screenshots were not the target pages ([MindStudio](https://www.mindstudio.ai/blog/how-to-build-jev-browser-agent)). Every "done" from Jev therefore needs independent verification. A security vendor called Jev "even more susceptible to attack" than LLMs after an attacker-controlled ad diverted it ([Computerworld](https://www.computerworld.com/article/4236138/typesafes-jev-even-more-susceptible-to-attack-than-llms-says-security-vendor-3.html)). Critics note that TypeSafe has published no calibration data behind its "zero hallucinations" claim ([KDnuggets](https://www.kdnuggets.com/what-everyone-is-getting-wrong-about-typesafe-ais-jev)). jev-browse also sends visible page text to `api.typesafe.ai` by default ([jev-browse](https://github.com/danielnc/jev-browse)), which matters when the pages are unreleased staging builds.

Jev fits only the live-navigation step, and the compile-and-replay design removes that step from repeat runs. A compiled regression run makes zero navigation decisions, so Jev has nothing to speed up. It can only help when a scenario is executed for the first time, or when a broken script is being repaired. In both cases the user's scenarios already spell out the clicks ("go there, click there"), which a Haiku 5.5 subagent can follow cheaply.

The case for Jev is strongest if most of the user's QA runs are one-off checks of new features that will never be re-run. In that case every run is a first run, and a 2–3x faster executor pays off. The right move is to put the browser executor behind an interface, ship it first on Playwright CLI or agent-browser, and then benchmark Jev on 5–10 of the user's own scenarios. damian87x/jev-browser-use ships a ready-made head-to-head script comparing a Jev fast path with a plain playwright-cli loop for QA checks ([GitHub](https://github.com/damian87x/jev-browser-use)). If "Jev" turns out to be a mishearing, the most likely intended tool is SawyerHood's **dev-browser** skill. Its author reports 3 min 53 s and $0.88 against Playwright MCP's $1.45 on one benchmark ([GitHub](https://github.com/sawyerhood/dev-browser)).

## Recommended architecture and phased build plan

### One skill, four scripts, three verdicts

The skill's `SKILL.md` should be a short orchestration checklist, kept under the documented 500-line guideline. Deterministic work goes into bundled scripts, which are "executed, not loaded" and so cost no context ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). Setting `disable-model-invocation: true` makes it run only when called as `/visual-qa`, which is sensible because it writes to Drive. It should start as a personal or project skill. It only needs to become a plugin when it must ship MCP configs, hooks or agents to teammates, because a plugin's components load into every session where it is enabled ([Claude Code plugins docs](https://code.claude.com/docs/en/plugins)).

```
visual-qa/
  SKILL.md                       # checklist: validate -> execute -> judge -> report -> upload
  reference/scenario-format.md
  reference/drive-setup.md       # one-time OAuth client setup, read only when auth fails
  templates/report.html.j2       # inline CSS, data-URI WebP screenshots, print CSS
  scripts/validate_scenarios.py  # schema check with verbose errors
  scripts/run_compiled.sh        # npx playwright test, parallel workers, writes results.json
  scripts/build_report.py        # results.json + screenshots -> report.html -> report.pdf
  scripts/drive_upload.py        # find-or-create QA/<date topic>, resumable upload, prints link
  compiled/<scenario-id>.spec.ts # generated once; original plain-language steps kept as comments
```

Scenarios use YAML with Gherkin meaning: Given is the starting state, When is the action, Then is an observable outcome, in about three to five steps ([Cucumber Gherkin reference](https://cucumber.io/docs/gherkin/reference/)). A separate `expected` field holds the text the report displays.

```yaml
topic: Checkout flow
base_url: https://staging.example.com
```

The pipeline runs in five stages. Only two of them use a model on a typical run, and one of those is skipped entirely when the compiled script still works:

| Stage | Done by | Model use | Output |
|---|---|---|---|
| Validate | `validate_scenarios.py` | None | Clean scenario list or precise errors |
| Execute | Compiled spec if it exists; otherwise a forked Haiku 5.5 or Sonnet 5.5 subagent acting on refs (Playwright CLI or agent-browser), which records the run as a new spec plus code assertions for the key points | Only on first run or after a script fails | Viewport PNG, optional full-page PNG, DOM excerpt, gate and assertion results |
| Judge | Fresh subagent, or a direct Haiku 5.5 API call from a script | One call per scenario, only for the visual key points | Evidence-first JSON: per-point met / not met / cannot determine |
| Reconcile and report | `build_report.py` | None | pass / fail / needs review per scenario; HTML, PDF, results.json |
| Deliver | `drive_upload.py` | None | Drive folder link printed to the session |

The repair path keeps the healer honest. When a compiled spec fails on a locator or a timeout, a repair subagent may patch locators and waits only, and every change is logged as a diff in the report. If an assertion fails, the result is reported as a fail and nothing is patched. This guards against the documented habit of healers loosening assertions, and against Playwright's healer marking a test "skipped" when it believes the feature is broken ([Playwright docs](https://playwright.dev/docs/test-agents)). A "skipped" result counts as a fail.

| 3. ## Conclusion

Compile-and-replay reverses the cost picture. Once a scenario is a Playwright script, navigation is free and the only recurring model spend is one judgment per scenario, measured in cents per suite. Jev and similar accelerators therefore speed up a step a mature version of this tool mostly stops paying for. Jev matters only in proportion to how many runs are genuinely new. The user's question about speed has a structural answer rather than a vendor answer: decide how much of the QA work is repeat regression and how much is one-off checking of new features, and that ratio decides whether a faster live executor is worth a third-party dependency.

The real product risk is a green report that lies, not the token bill. The published evidence says screenshot judges are agreeable, so the skill's value lies in its calibration. That means code checks that can fail independently of the model, a "needs review" verdict used honestly, and a labelled set of deliberately broken scenarios run on every change to the judge. The best measure of quality is the false-pass rate on that set, not speed or cost. The Drive limitation also helps here: a PDF of evidence and verdicts is the version people will actually open and share, and the HTML becomes the archive copy.
